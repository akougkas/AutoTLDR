Build specification · v1 · 30 August 2026

The mixed folder,
fused and cited.

The v1 target: point AutoTLDR at a folder of mixed text documents and learn what the collection is, how the pieces relate, and where every claim came from.

Tier 0 · text-shaped Tier 1 · document-shaped Tier 2 · collections Tier 3 · data-shaped Tier 4 · visual Tier 5 · temporal Tier 6 · opaque

Implementation status: the thin Stage 1–8 MVP is implemented. One public pipeline acquires files, folders, archives, stdin and URLs, normalizes every supported input into the same addressable representation, applies the measured role and fusion policy, optionally accepts strictly ID-grounded local-model claims, and renders six output shapes. Watch, MCP, the Agent Skill and A2A metadata wrap that pipeline. The software gate is complete; independent physical proof of zero CPU spill remains unavailable from the current LM Studio and process telemetry, and it is reported separately rather than invented.

Part 1

Two modes, one engine

Mode 1

Invoke

$ autotldr report.pdf $ printf '# Notes\nhello\n' | autotldr - --type md $ autotldr https://docs.example.com/guide --out md $ autotldr paper.pdf analysis.ipynb results.xlsx

Synchronous. Feels like cat for Tier 0 and remains bounded for Tier 1. Two or more explicit inputs are fused as a Stage 4 collection. Writes to stdout by default.

Mode 2

Watch

$ autotldr watch ./inbox --once $ autotldr watch ./inbox --status $ autotldr watch ./inbox --recursive --debounce 10

A foreground polling service monitors one folder. Drop a file in and a per-file artifact appears under .autotldr/files/ without anyone asking. The fused .autotldr/FOLDER.tldr.md roll-up is rebuilt on a debounce, so twelve files dropped produce one rebuild. This is the service.

This is what the "auto" means. Invoke mode is a tool and there are other tools. Watch mode turns a directory into a self-summarizing corpus, and it is the differentiated half.

Part 2

Stack decisions

Language: Python, distributed with uv

The extraction ecosystem this depends on is Python: MarkItDown, Docling, openpyxl, pypdf, pymupdf, pinned tree-sitter bindings, h5py and trafilatura, alongside stdlib OOXML, JSON and HTML adapters where a smaller native parser preserves the required structure. Rust would give a faster cold start and a static binary, and would cost most of year one reimplementing extractors that already exist and are maintained.

The cost, named. Python startup is the one thing that can make this feel unlike a Unix tool, so the mitigation is not optional. Every extractor is lazy-imported; autotldr notes.md must never import Docling, h5py, or a tokenizer. The entry path imports only standard-library argument, path and stream primitives until the router has decided what the input is.

Budget: under 120ms to first output for a Tier 0 file. A tested contract, not an aspiration. If it regresses, that is a build failure. The migration path, if it ever comes to that, is a Rust core calling Python extractors as subprocesses, and the CLI contract is designed so that swap is invisible to callers.

Store: SQLite as the durable store, DuckDB as a compute engine

ComponentRole
SQLite, WAL modeThe durable store: semantic units, relations, folder state, job queue, content-addressed cache
FTS5Lexical index over unit content. BM25 out of the box
sqlite-vecVector index over unit embeddings, in the same file
Recursive CTEsThe relation graph. Unit-to-unit, formula dependencies, import edges
DuckDBInvoked transiently to profile a data file. Never a persistent store. It reads CSV, Parquet, JSON and Excel directly off disk with zero ingestion, so Tier 3 profiling is a query rather than a parse-and-load pipeline

One durable file per project at .autotldr/store.db. Opens in microseconds. Concurrent readers alongside the daemon's writer, which is exactly what WAL mode is for. DuckDB is spun up, asked a question, and closed, so its single-writer limitation never bites.

The SurrealDB verdict

What is genuinely attractive. SurrealDB 3.0 went GA in February 2026 with $44M raised and one engine covering document, graph, relational, full-text and vector through a single query language and a single transaction. For a system whose representation is explicitly a graph of typed units with both lexical and vector retrieval, that is the shape of the problem. Its live-query feature is a natural fit for the watch daemon. Architecturally it is the most elegant answer on the table.

Why not for v1Detail
No zero-ingestion file readingTiers 0–3 are mostly files. DuckDB querying an XLSX in place is a structural advantage SurrealDB has no answer to, and it is worth more here than multi-model unification
Vector indexing still maturingSurrealDB describes the 3.0 indexing work as a foundation for future specialized indexes, vector among them. Building the retrieval core on a roadmap item is avoidable risk
No independent embedded benchmarksNearly all published technical detail traces back to SurrealDB's own material, and the funding is openly earmarked for hardening reliability and performance. That is candid, and it is the wrong place for a foundational bet in month one
Startup costA CLI that must answer in 120ms cannot afford an engine designed to also run distributed clusters

When to revisit, concretely. If the watch daemon grows into a persistent multi-folder service with live subscriptions and cross-project queries, SurrealDB's live queries and unified model become a real advantage over hand-rolling that on SQLite. The storage layer stays behind one interface so this remains a swap rather than a rewrite. Revisit at the point where the daemon, not the CLI, is the primary entry point.

Ruled out and why. LanceDB is excellent at vectors and solves a problem we do not have at v1 scale. Kùzu is the right call if graph traversal becomes the bottleneck, and recursive CTEs over a few thousand units will not be that. Postgres with pgvector needs a server, which is disqualifying for a Unix tool, and Chroma and Qdrant are servers for the same reason.

Extraction: a router, not a converter

No single extractor wins across formats, and accuracy gaps above 20% between parsers on complex layouts are normal. So AutoTLDR routes.

InputExtractorWhy this one

“Source code” is not an open-ended format claim. The reliable inventory is Python via the stdlib AST, then JS/JSX, TS/TSX, C/C++, Java, Rust, Go, Ruby, PHP, Kotlin, C#, Bash, SQL, Scala, Perl (with parser evidence), R, Elixir, Haskell, and Objective-C (with parser evidence) through the pinned native tree-sitter pack. For Perl and Objective-C, evidence means an error-free native declaration or import node grounds the emitted unit; without it, the file is declined rather than treated as empty success.

Named Tier 0 declines include Lua, Swift, Zsh, Fish, Dart, Clojure/ClojureScript, F#, VB, Groovy, Vue, Svelte, and Objective-C++. Every other unconfigured or unreliable language follows the same named-decline path and is not part of the supported inventory.

Two routing rules govern v1. Native format beats conversion: routing an XLSX through a PDF-oriented pipeline throws away exactly the structure that carries the meaning, and the same holds for DOCX comments and notebook outputs. The fast path is the default: Stage 3 implements that path. A future --deep opts into the slow accurate extractor, and a user who has not asked to wait does not wait.

Models, measured by the job they perform

Jobv1 approach
Structure extractionNo model. Parsers, all tiers

Role taggingMeasured routing: rules prove assumption; opt-in local adds procedure; configured frontier enrichment adds six named roles

Stage 2 settled role tagging. On 200 exact units across five formats, a role passed only with support at least 15, at least three source groups, precision at least 0.80, and recall at least 0.70. Aggregate accuracy was not a gate.

Rules passed assumption; selected local Ornith passed procedure and the unknown fallback; the frontier ceiling passed definition, procedure, caveat, example, decision, and limitation. claim, parameter, and result passed no arm and were removed. Reliability is backend-scoped; anything the running backend did not prove remains unknown.

Deterministic extraction and measured fusion remain useful with every model turned off. They are the fallback and source of truth. Stage 5 added the grounded model-written TLDR on top of them; ZBook evaluation loads one AutoTLDR-owned generation model at a time, requires 100% GPU offload, runs candidates sequentially, and unloads the owned model afterward. Independent certification that nothing spilled to CPU is still unavailable, and the certification wrapper fails closed rather than accept a configuration-only GPU claim.

Part 4

Fusion, the actual wedge

Stage 4 is implemented and measured. It fuses two or more explicitly named sources with no model. Stage 5 then supplied what the fusion core deliberately left out: bounded directory, repository, archive and documentation-site acquisition, and the model-written semantic collection statement.

Per-file summarization is a commodity. Fusing a folder into one representation is what nobody does, and it is why this scope was chosen. Concretely, for a folder holding a paper, a spreadsheet of results, and the code that produced them, four linking signals run cheapest first.

  1. Literal reference. A filename, path, URL, DOI or citation key in one file naming another. Exact, high precision, catches most real links. no model
  2. Identifier co-occurrence. A column header tput_mbps, a symbol measure_throughput(), and a caption "Throughput (Mb/s)". Normalized token matching over identifiers. no model
  3. Structural correspondence. A results table whose column count and row labels match a dataset's schema. A figure numbered to match a notebook cell's output. Cheap and surprisingly strong. no model
  4. Semantic similarity. Proposed embedding fallback for concepts sharing no tokens. It is not implemented or resident for the first complete demo and may enter only after a separate frozen eval proves value. deferred

Signals 1 through 3 run with no model. The one immutable scored run judged every output class separately; aggregate accuracy was neither computed nor used. The user-facing path applies the frozen dispositions below, while the raw analyzer remains available for future fresh-corpus evaluation.

Stage 5 closed this on 31 August 2026. It sends a bounded evidence pack to one measured local generation model, accepts only strict claims over existing unit IDs, derives origins itself, and applies the existing exact complete-output budget. The Borealis fixture routed 14 mixed inputs into 135 units, 105 relations and 15 gaps, and one ZBook-local Ornith-1.5-35B-A3B instance returned three fully cited claims with no fallback. All six output shapes came from that one synthesis, and 63 independent checks over the saved artifacts passed.

Part 7

Decisions locked

Two decisions that were expensive to reverse, both now settled and shipped.

Decision 1

The watch daemon ships in v1

It is the differentiated half and roughly two weeks that overlap with nothing else. Invoke-only ships a usable tool in five weeks; including watch makes it seven and makes the first release tell a complete story.

It is in, because "auto" is in the name and a tool without it is a worse version of things that already exist. Stage 6 delivered it.

Decision 2

A watched folder produces a per-file artifact plus a roll-up

The options were a single rolling FOLDER.tldr.md that gets rewritten; a per-file artifact plus a folder roll-up; or a versioned history so you can see how the collection's story changed as files arrived.

Per-file plus roll-up won for v1, with versioning deferred. Each dropped file gets its own artifact and FOLDER.tldr.md holds the fused view, rewritten on debounce. The third option is the most interesting and the most work.
