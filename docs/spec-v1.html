Part 1

Two modes, one engine

Mode 1

Invoke

$ autotldr report.pdf $ autotldr ./project $ autotldr ./project --ask "what did we measure" $ autotldr https://docs.example.com/guide

Synchronous. Feels like cat for Tier 0, a couple of seconds for Tiers 1–3. Writes to stdout by default. This is the tool.

Mode 2

Watch

$ autotldr watch ./inbox --out bundle $ autotldr watch --status $ autotldr watch --stop ./inbox

A daemon monitors registered folders. Drop a file in and an artifact appears without anyone asking. Re-fusion runs on a debounce, so twelve files dropped produce one rebuild. This is the service.

This is what the "auto" means. Invoke mode is a tool and there are other tools. Watch mode turns a directory into a self-summarizing corpus, and it is the differentiated half.

Part 2

Stack decisions

Language: Python, distributed with uv

The entire extraction ecosystem this depends on is Python: MarkItDown, Docling, openpyxl, pypdf, pymupdf, python-docx, nbformat, tree-sitter bindings, h5py, trafilatura. Rust would give a faster cold start and a static binary, and would cost most of year one reimplementing extractors that already exist and are maintained.

The cost, named. Python startup is the one thing that can make this feel unlike a Unix tool, so the mitigation is not optional. Every extractor is lazy-imported; autotldr notes.md must never import Docling, h5py, or a tokenizer. The entry path imports argparse, pathlib and sqlite3 and nothing else until the router has decided what the input is.

Budget: under 120ms to first output for a Tier 0 file. A tested contract, not an aspiration. If it regresses, that is a build failure. The migration path, if it ever comes to that, is a Rust core calling Python extractors as subprocesses, and the CLI contract is designed so that swap is invisible to callers.

Store: SQLite as the durable store, DuckDB as a compute engine

ComponentRole
SQLite, WAL modeThe durable store: semantic units, relations, folder state, job queue, content-addressed cache
FTS5Lexical index over unit content. BM25 out of the box
sqlite-vecVector index over unit embeddings, in the same file
Recursive CTEsThe relation graph. Unit-to-unit, formula dependencies, import edges
DuckDBInvoked transiently to profile a data file. Never a persistent store. It reads CSV, Parquet, JSON and Excel directly off disk with zero ingestion, so Tier 3 profiling is a query rather than a parse-and-load pipeline

One durable file per project at .autotldr/store.db. Opens in microseconds. Concurrent readers alongside the daemon's writer, which is exactly what WAL mode is for. DuckDB is spun up, asked a question, and closed, so its single-writer limitation never bites.

The SurrealDB verdict

What is genuinely attractive. SurrealDB 3.0 went GA in February 2026 with $44M raised and one engine covering document, graph, relational, full-text and vector through a single query language and a single transaction. For a system whose representation is explicitly a graph of typed units with both lexical and vector retrieval, that is the shape of the problem. Its live-query feature is a natural fit for the watch daemon. Architecturally it is the most elegant answer on the table.

Why not for v1Detail
No zero-ingestion file readingTiers 0–3 are mostly files. DuckDB querying an XLSX in place is a structural advantage SurrealDB has no answer to, and it is worth more here than multi-model unification
Vector indexing still maturingSurrealDB describes the 3.0 indexing work as a foundation for future specialized indexes, vector among them. Building the retrieval core on a roadmap item is avoidable risk
No independent embedded benchmarksNearly all published technical detail traces back to SurrealDB's own material, and the funding is openly earmarked for hardening reliability and performance. That is candid, and it is the wrong place for a foundational bet in month one
Startup costA CLI that must answer in 120ms cannot afford an engine designed to also run distributed clusters

When to revisit, concretely. If the watch daemon grows into a persistent multi-folder service with live subscriptions and cross-project queries, SurrealDB's live queries and unified model become a real advantage over hand-rolling that on SQLite. The storage layer stays behind one interface so this remains a swap rather than a rewrite. Revisit at the point where the daemon, not the CLI, is the primary entry point.

Ruled out and why. LanceDB is excellent at vectors and solves a problem we do not have at v1 scale. Kùzu is the right call if graph traversal becomes the bottleneck, and recursive CTEs over a few thousand units will not be that. Postgres with pgvector needs a server, which is disqualifying for a Unix tool, and Chroma and Qdrant are servers for the same reason.

Extraction: a router, not a converter

No single extractor wins across formats, and accuracy gaps above 20% between parsers on complex layouts are normal. So AutoTLDR routes.

InputExtractorWhy this one
Markdown, txt, rSTNative parseStructure is already there
Source codetree-sitterSymbols and signatures, not text
JSON, YAML, TOML, XMLStructural inductionSchema is the semantics
CSV, ParquetDuckDB profilingZero-copy. Statistics, not rows
XLSXopenpyxl on the formula layerNever through a markdown converter. The formula graph is the meaning and conversion destroys it
DOCXpython-docxNative structure, tracked changes, comments
PDF, simplepymupdf text layerFast path. Most PDFs
PDF, table-heavyDocling, opt-in via --deepAccurate and slow. Earn the wait
HTML, URLllms.txt probe, then trafilaturaCheck for a served summary before crawling
NotebooksnbformatCells, outputs, and their pairing
HDF5, NetCDFh5py, netCDF4Structure and attributes, never values

Two rules the router enforces. Native format beats conversion: routing an XLSX through a PDF-oriented pipeline throws away exactly the structure that carries the meaning, and the same holds for DOCX comments and notebook outputs. The fast path is the default: --deep opts into the slow accurate extractor, and a user who has not asked to wait does not wait.

Models, and the one thing that must be proven first

Jobv1 approach
Structure extractionNo model. Parsers, all tiers
Schema and statisticsNo model. DuckDB and profiling
Formula graphNo model. openpyxl dependency walk
Role taggingRules and heuristics first, small local model where rules fail
Embeddings for fusionLocal Qwen3-Embedding, small variant, ONNX
Folder-level synthesisLocal 3–4B, or a configured OpenAI-compatible endpoint

The honest position on role tagging. Distinguishing a claim from a caveat from an assumption is the load-bearing capability of the whole representation, and a 3B model may simply not be reliable at it. Current guidance puts 1.5B–3B as the floor for extraction work and Qwen3.5 4B as the CPU sweet spot, but that is general guidance, not evidence about this task.

So role tagging gets an eval before it gets an implementation: 200 hand-labeled spans across five formats, scored against rules-only, a 4B local model, and a frontier model as ceiling. If rules-only lands close to the 4B, v1 ships with rules and stays fully offline and instant. If neither approaches the ceiling, the taxonomy shrinks to whatever is reliably extractable, and the product claim shrinks with it.

Nothing in Tiers 0–3 requires a model to produce a useful result. That is why this scope was the right pick: v1 degrades to a genuinely valuable tool even with every model turned off.

Part 4

Fusion, the actual wedge

Per-file summarization is a commodity. Fusing a folder into one representation is what nobody does, and it is why this scope was chosen. Concretely, for a folder holding a paper, a spreadsheet of results, and the code that produced them, four linking signals run cheapest first.

  1. Literal reference. A filename, path, URL, DOI or citation key in one file naming another. Exact, high precision, catches most real links. no model
  2. Identifier co-occurrence. A column header tput_mbps, a symbol measure_throughput(), and a caption "Throughput (Mb/s)". Normalized token matching over identifiers. no model
  3. Structural correspondence. A results table whose column count and row labels match a dataset's schema. A figure numbered to match a notebook cell's output. Cheap and surprisingly strong. no model
  4. Semantic similarity. Embedding proximity across files, as the fallback for concepts sharing no tokens. The only signal that costs a model and the only one that produces false positives, so it carries the lowest confidence and is always reported as inferred. embeddings

Signals 1 through 3 run with no model at all. If the eval shows they carry most of the value, v1 fusion is fully offline and deterministic, which would be a real product advantage rather than a limitation.

What fusion emits

OutputWhat it is
Collection statementWhat this folder is for, grounded in its contents
Relation graphWhich file produced which, which claim rests on which data, which code implements which method
ContradictionsThe paper says n=40, the CSV has 38 rows. The single most valuable output the tool can produce, and it falls directly out of having both in one representation
OrphansFiles nothing else references. Often the stale draft nobody deleted
GapsConcepts referenced but never defined anywhere in the collection

Contradiction detection is the demo. It is also the thing that requires no clever summarization, only a shared representation and a comparison.

Part 7

Open forks

Two decisions made provisionally, both cheap to settle now and expensive to reverse later.

Fork 1

Is the watch daemon in the first release?

It is the differentiated half and roughly two weeks that overlap with nothing else. Invoke-only ships a usable tool in five weeks; including watch makes it seven and makes the first release tell a complete story.

I lean toward including it, because "auto" is in the name and a tool without it is a worse version of things that already exist.

Fork 2

What artifact does a watched folder produce?

A single rolling FOLDER.tldr.md that gets rewritten; a per-file artifact plus a folder roll-up; or a versioned history so you can see how the collection's story changed as files arrived.

I lean toward per-file plus roll-up for v1, with versioning deferred. The third is the most interesting and the most work.
